059: 1. Executive Summary & Strategic Rationale
060: 1.1 Product Vision
061: Embedded and IoT devices — home and enterprise routers, IP cameras, and industrial control systems — run firmware that is rarely patched, heavily reused across product lines, and built from old C/C++ toolchains with weak memory-safety guarantees. The firmware supply chain is opaque: a single vulnerable component, a hardcoded credential, or a deprecated cryptographic primitive can propagate across millions of shipped devices and remain exploitable for years. Finding these defects today depends on a small population of highly skilled reverse engineers performing slow, manual, per-image analysis. That approach cannot keep pace with the volume of firmware a vendor, enterprise, or research team must vet before deployment.
062: Project Unit42-FirmwareX moves firmware assurance from manual reverse engineering to an automated binary-analysis and emulation pipeline. The engine unpacks a firmware image, emulates its binaries across CPU architectures, applies symbolic execution and taint analysis to trace attacker-controllable input to dangerous memory sinks, and scans for hardcoded secrets and weak cryptography — producing a structured, CWE-classified report of memory-safety and posture defects. Every stage runs inside an isolated, non-network-routed sandbox, and the engine never weaponises what it finds: crash conditions are captured as diagnostic state for human validation, not turned into working exploits.
063: 1.2 Core Value Proposition
064: Proactive, pre-deployment assurance. Memory-safety defects and posture weaknesses are identified across firmware images before devices ship, at a scale manual reverse engineering cannot match.
065: Consistent and repeatable. Every image is analysed the same way, producing auditable, comparable results rather than analyst-dependent findings.
066: A force multiplier for scarce expertise. Automated triage focuses expensive reverse-engineering effort on the findings that actually warrant human attention.
067: Supply-chain visibility. Reused vulnerable components and secrets are surfaced across many images, closing a blind spot in embedded supply-chain security.

084: 2. What You Are Building
085: In plain terms, you are building a pipeline that takes a firmware image file, pulls it apart, runs its binaries safely in an emulated sandbox, analyses them for memory-corruption risk, hardcoded secrets and weak cryptography, and produces a structured vulnerability report with a dashboard to explore it. You run it only against publicly available, open-source IoT firmware, inside an isolated sandbox that has no route to any live network or device.
086: The engine performs five things in sequence, and your job is to deliver a working vertical slice through all of them:
087: Unpack the firmware image — identify its format and carve out the embedded filesystems (SquashFS, CramFS, UBIFS, JFFS2 and friends), reconstructing the root filesystem.
088: Audit every extracted executable statically — architecture, endianness, and the binary-hardening matrix (NX/DEP, stack canaries, RELRO, PIE/ASLR).
089: Emulate the binaries across architectures (MIPS, ARM32, ARM64, x86_64) inside containerised QEMU nodes, bringing up network services where possible.
090: Analyse with symbolic execution and taint analysis — trace attacker-controllable input to dangerous sinks, and fuzz emulated services to surface crash conditions, capturing non-weaponised crash state.
091: Report every finding as a structured, CWE-classified record, served through an API and a dashboard with a file tree, mitigation matrix, CFG viewer and crash log.
092: Scoped to be delivered by one engineer in four weeks
093: Firmware analysis is a hard domain, so this project is bounded to be completable by a single capable engineer in four weeks — handling the common cases well and degrading gracefully on the hard ones:
094: • Linux-based IoT firmware first. Target the common router/camera class; MIPS and ARM are the priority architectures.
095: • Bounded analysis. Full-system emulation of arbitrary firmware and exhaustive symbolic execution are open research problems — you bound them with budgets and best-effort fallbacks, not promises of completeness.
096: • Public firmware only. Open-source images you are licensed to examine, analysed in an isolated sandbox. Never a live device, never a network you do not own.
097: • Analysis, not weaponisation. The engine produces diagnostic crash state and findings for a human to validate — never a functional exploit, PoC weapon, or shellcode.

120: 4. Scope and Boundaries
121: 4.1 In Scope
122: Publicly available, open-source IoT firmware images you are licensed to analyse.
123: Unpacking common firmware containers and filesystems, including multi-stage compression and custom headers.
124: Static hardening audit of extracted ELF binaries and a per-binary mitigation matrix.
125: User-mode and best-effort full-system emulation for MIPS, ARM32, ARM64 and x86_64 inside containerised QEMU nodes.
126: Bounded symbolic execution and taint analysis tracing input sources to memory sinks on selected binaries.
127: Hardcoded-secret and weak-cryptography scanning with output redaction.
128: Protocol-aware fuzzing (HTTP/UPnP/MQTT) of emulated services to surface crash conditions.
129: A REST/gRPC API, a dashboard, and structured CWE-classified reporting.
130: 4.2 Out of Scope
131: Firmware you are not licensed to examine. Only public, open-source images.
132: Any testing against live or physical devices or real networks. Analysis happens only against image files in the sandbox.
133: Functional exploits, weaponised proof-of-concepts, or shellcode. The engine produces diagnostic crash state for validation, never a working exploit.
134: Distribution of extracted proprietary IP or real secrets. Discovered secrets are redacted and stored as fingerprints by default.
135: Guaranteed full-system emulation of arbitrary firmware. This is an open research problem; the engine is best-effort with graceful fallback.
136: Kernel, bootloader or driver exploitation. Focus is user-space binaries and network services.
137: 4.3 Safety Boundaries (non-negotiable)
138: Hard guardrails — enforced in code, not policy documents
139: No network egress from analysis workers. Emulation and analysis run in sandboxes with no route to external networks; emulated service networks are contained and non-routed.
140: Per-job resource quotas. CPU, memory and wall-clock limits per analysis job, terminated on breach, to prevent denial-of-service and runaway symbolic execution.
141: Output sanitisation. Discovered credentials, keys, certificates and proprietary strings are automatically redacted in stored and displayed output; only hashes/fingerprints are retained by default.
142: Non-weaponised artefacts only. Crash artefacts are register/stack state, offsets and tainted paths for human validation — not exploit code.
143: Immutable audit log. Every analysis job — inputs, parameters, artefacts, findings — is recorded in an append-only log.
144: 5. System Architecture & High-Level Design
145: 5.1 Component Overview
146: The engine is a control plane plus four analysis subsystems, fronted by an API and backed by a task queue and datastore. Long-running analysis runs as isolated workers pulled from the queue, each subject to the containment guardrails.
147: Unpacking & File System Extractor Engine. Deconstructs firmware binaries — identifies the container, carves embedded filesystems (SquashFS, CramFS, UBIFS, JFFS2, cpio, ext), and reconstructs the root filesystem and a file inventory.
148: Cross-Architecture Emulation Controller. A QEMU/Unicorn-based system- and user-mode emulation layer that runs extracted binaries for MIPS/ARM/x86 inside containerised nodes and brings up emulated network services.
149: Dynamic & Symbolic Analysis Runner. Automated taint analysis and path exploration via a symbolic-execution engine (angr), tracing user-controlled input to memory sinks and producing non-weaponised crash-state reports; also drives protocol-aware fuzzing.
150: Cryptographic & Secret Scanner. Automated discovery of hardcoded API keys, private certificates and credentials, and detection of weak/deprecated hashing and cryptographic primitives.

270: 7. Guardrails, Safety Controls & Containment
271: 7.1 Execution Isolation
272: ID
273: Control
274: Target / acceptance
275: SC-1.1
276: All binary execution and emulation occur inside isolated Docker/KVM sandboxes with no route to external networks.
277: Workers have zero outbound egress; verified by test.
278: SC-1.2
279: Emulated service networks are contained and non-routed; fuzzing traffic never leaves the sandbox.
280: No packet escapes the analysis network.
281: SC-1.3
282: Untrusted binaries run under least privilege with a restricted syscall surface.
283: Container profile denies host access.
284: 7.2 Resource Quotas
285: ID
286: Control
287: Target / acceptance
288: SC-2.1
289: Per-job CPU, memory and wall-clock limits, enforced and terminated on breach.
290: No single job exceeds its quota or stalls the system.
291: SC-2.2
292: Symbolic-execution budgets (states, depth, time) prevent infinite loops and path explosion.
293: Runaway analysis is bounded and reported as incomplete.
294: SC-2.3
295: Queue-level concurrency and back-pressure prevent resource exhaustion across jobs.
296: System remains responsive under load.
297: 7.3 Output Sanitisation
298: ID
299: Control
300: Target / acceptance
301: SC-3.1
302: Automatic redaction of discovered secrets (keys, passwords, certificates) and proprietary IP in stored and displayed output.
303: Raw secrets never persisted in plaintext by default.
304: SC-3.2
305: Secrets retained as salted hashes/fingerprints so findings remain actionable without exposing the value.
306: Findings reference fingerprints, not values.
307: SC-3.3
308: Access to any unredacted artefact is gated and audited.
309: Every reveal is authorised and logged.

573: Appendix B — CWE Reference Mapping
574: The finding categories map to the following common weakness classes for embedded firmware. IDs are for classification only.
575: CWE
576: Name
577: Where it shows up in firmware
578: CWE-120
579: Buffer Copy without Checking Size
580: Classic unbounded strcpy/memcpy into fixed buffers.
581: CWE-121 / 122
582: Stack / Heap-based Buffer Overflow
583: Overflow in stack frames or heap allocations reached from input.
584: CWE-787
585: Out-of-bounds Write
586: Writes past allocation bounds; a frequent memory-corruption root cause.
587: CWE-134
588: Uncontrolled Format String
589: User input passed as a format string to printf-family functions.
590: CWE-78
591: OS Command Injection
592: Attacker-controlled input reaching system()/popen().
593: CWE-798 / 259
594: Use of Hardcoded Credentials / Password
595: Embedded usernames, passwords or API keys in binaries or configs.
596: CWE-321
597: Use of Hardcoded Cryptographic Key
598: Private keys or certificates shipped inside firmware.
599: CWE-327 / 328
600: Broken/Risky Crypto · Weak Hash
601: Deprecated ciphers or weak hashing (e.g., MD5/SHA-1 for security).
602: CWE-1277
603: Firmware Not Updateable
604: No secure update path, extending the exposure window.
605: Appendix C — Glossary
606: Term
607: Meaning
608: Firmware image
609: The packaged software (kernel, filesystem, binaries) that runs a device, distributed as a .bin/.img file.
610: SquashFS / CramFS / UBIFS / JFFS2
611: Compressed/embedded filesystems commonly packed inside IoT firmware.
612: ELF
613: Executable and Linkable Format — the binary format for the firmware's programs and libraries.
614: NX / DEP
615: Marks memory non-executable, hindering code execution from data regions.
616: ASLR / PIE
617: Address-space layout randomisation; PIE lets the main binary be randomised.
618: RELRO
619: Read-only relocations; hardens the GOT against overwrite (partial or full).
620: Stack canary
621: A guard value that detects stack-buffer overflows before return.
622: Emulation (QEMU/Unicorn)
623: Running a binary built for one CPU architecture on another, in software.
624: Symbolic execution
625: Exploring program paths with symbolic (not concrete) inputs to reason about reachability.
626: Taint analysis
627: Tracking attacker-controllable data through a program to dangerous sinks.
628: Sink
629: A sensitive operation (e.g., strcpy, system) where tainted input can cause harm.
630: Fuzzing
631: Feeding malformed/random inputs to find crash conditions.
632: CWE
633: Common Weakness Enumeration — a catalogue of software weakness types.
634: CFG
635: Control-flow graph — a map of a program's possible execution paths.
