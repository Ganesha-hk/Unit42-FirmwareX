# OpenWrt 24.10.4 supported profile

The representative image is `openwrt-24.10.4-x86-64-generic-squashfs-rootfs.img.gz` (SHA-256 `8c88c338afad0535ab295a62e9555dc91f3bf5c8f4fc3bc67008adb2619f60e6`). The frozen corpus manifest records the download source and all six corpus images. This profile is enabled only when that exact image hash and the following extracted binary hashes match:

| Binary | SHA-256 | Selected check |
| --- | --- | --- |
| `/bin/busybox` | `2f05c4e66e4edab3914b24e00a8c016db2b65f4165b56b7842b359c5c1f55e8c` | Run the `true` applet with the extracted guest libraries; require exit 0. |
| `/usr/sbin/uhttpd` | `02723a581496090ccc5d8b19da6bdd0e8fa8878e148dd99ae6be6c13fc5aa94b` | Start with extracted libraries and synthetic document root; request `/index.html` over job-private loopback; require HTTP 200 and the exact marker; record startup, request, response and process cleanup. |
| `/usr/libexec/cgi-io` | `897d4abfc18c8c679f5cb3657fb67080ecd75b00288f7e25a59f75c4b06ced0f` | Symbolically enter the CFG-identified `main` at `0x402003` with `argc=1` and `argv[0]=/usr/libexec/cgi-upload`; require modeled `getenv` data to reach `strcpy`. |

The entire extracted image contains 171 eligible ELF candidates. The selected checks cover three binaries; `cgi-io` has a symbolic check but no concrete request/response service check. `uhttpd` has a concrete service check but no symbolic profile. BusyBox has an applet check, not a service protocol check. Other corpus images use the bounded generic analysis and do not inherit this fixed-address profile.

The `cgi-io` profile verifies one narrow valid path: a POST request with `CONTENT_LENGTH=0` and a `CONTENT_TYPE` beginning `multipart/form-data; boundary=`. It returns EOF for standard input, uses a valid argv, named/missing environment behavior, a writable errno location, and `/` as its symbolic working directory. The selected copy allocates `strlen(boundary) + 3`, writes the two-byte `--` prefix, then copies the boundary and terminator. The engine now recognizes that relationship, so this path produces no CWE-120 candidate and no artificial null-write diagnostic. The direct isolated run completes in 54 steps with one path, terminal return `0`, and no findings.

This is a bounded header and empty-body check, not full multipart upload coverage. It does not explore body parsing, filesystem interactions, authentication, or all CGI branches. The dashboard reports `input_scope=multipart_header_empty_body` and **Selected checks complete** only because all three declared selected checks finished; that label does not claim whole-firmware coverage.

To reproduce, start the local stack as described in [README.md](../README.md), then run `scripts/verify-openwrt-demo.cjs` with `FWX_PLAYWRIGHT_MODULE` pointing to Playwright and `FWX_EVIDENCE_DIR` pointing to a fresh evidence directory. The browser script uploads the real image, waits for extraction and analysis, checks the HTTP and symbolic results including terminal return `0`, opens the saved report, and records a screenshot, video, and report JSON. The corrected run is in `evidence/openwrt-final-gap-fix-2026-11-10/`. The dashboard says **Selected checks complete** because each declared selected check completed; it does not claim whole-firmware coverage. Earlier reports remain historical evidence and are not rewritten.

The isolated unit suite passed 159 tests. The six controlled classification cases passed, including a safe symbolic case, a null-write case, a proven out-of-bounds source-to-sink case, and heuristic static/scanner classifications. Compiled fixtures verify arguments, absent/concrete variables, stable repeated environment reads, writable errno storage, zero-length standard-input EOF, safe `strlen(input)+3` copying, and detection of an undersized `strlen(input)+2` allocation. The generic firmware startup fallback is also regression tested. These checks do not establish zero false positives on arbitrary firmware.
